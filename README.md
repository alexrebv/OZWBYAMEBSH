# Синхронизация FBS в Google Sheets

Один сервис вместо шести скриптов Apps Script. Тянет продажи и остатки FBS
из Ozon, Wildberries и Яндекс Маркета и складывает в одну таблицу.

Управление — с листа **«Настройки»** в самой таблице. Чтобы включить задачу,
поставь `1` в колонку «Вкл». Перезапускать сервис не нужно: он перечитывает
настройки каждую минуту.

## Что нужно один раз настроить

### 1. Сервисный аккаунт Google

1. [console.cloud.google.com](https://console.cloud.google.com) → создать проект.
2. APIs & Services → Library → включить **Google Sheets API**.
3. APIs & Services → Credentials → Create credentials → **Service account**.
4. У созданного аккаунта: Keys → Add key → JSON. Файл скачается.
5. Открыть таблицу и дать доступ **Редактор** на почту вида
   `имя@проект.iam.gserviceaccount.com` из этого файла.

Ключ удобно закодировать в одну строку:

```bash
base64 -w0 service-account.json
```

### 2. GitHub

```bash
git init
git add .
git commit -m "первая версия"
git branch -M main
git remote add origin git@github.com:ВАШ_АККАУНТ/mp-sync.git
git push -u origin main
```

Файл `.env` в репозиторий не попадёт — он в `.gitignore`.

### 3. Railway

1. [railway.app](https://railway.app) → New Project → **Deploy from GitHub repo**.
2. Выбрать репозиторий. Nixpacks соберёт проект сам, `railway.json` уже лежит рядом.
3. Variables → добавить:

   | Переменная | Значение |
   |---|---|
   | `SHEET_ID` | id таблицы из её адреса, между `/d/` и `/edit` |
   | `GOOGLE_SERVICE_ACCOUNT_JSON` | вывод команды base64 выше |

4. Settings → убедиться, что сервис работает как **worker** без публичного порта.

Ключи маркетплейсов можно положить сюда же переменными
`OZON_CLIENT_ID`, `OZON_API_KEY`, `WB_API_KEY`, `YM_API_KEY`, `YM_CAMPAIGN_ID` —
тогда они перебьют значения из таблицы. Так безопаснее: в таблицу ключи видят все,
у кого есть доступ на просмотр.

## Лист «Настройки»

Блок параметров, строки 2–18:

| Параметр | Значение |
|---|---|
| OZON Client-Id | |
| OZON Api-Key | |
| WB Api-Key | |
| Яндекс Api-Key | |
| Яндекс campaignId | |
| Яндекс campaignId FBY | |
| Рестарт | |

Блок параметров читается из строк **2–20**. Параметр вне этих строк сервис не увидит.

**Рестарт** — поставьте `1`, и на ближайшей минутной проверке сервис погасит ячейку
и выйдет; Railway поднимет его заново. Флаг гасится до выхода, поэтому срабатывает
один раз. Оговорка: если процесс завис намертво, он не прочитает и этот флаг —
тогда помогает только перезапуск из панели Railway.

Блок задач, начиная со строки 21:

| Задача | Вкл | Каждые, мин | Глубина, дней | Последний запуск | Результат | С даты |
|---|---|---|---|---|---|---|
| OZON продажи | 1 | 15 | 3 | заполняется сервисом | заполняется сервисом | |
| OZON остатки | 1 | 60 | | | | |
| WB продажи | 1 | 15 | 7 | | | |
| WB остатки | 1 | 60 | | | | |
| Яндекс продажи | 1 | 30 | 14 | | | |
| Яндекс остатки | 1 | 60 | | | | |
| OZON FBO продажи | 1 | 60 | 7 | | | |
| OZON FBO остатки | 1 | 60 | | | | |
| WB FBO продажи | 1 | 60 | 7 | | | |
| WB FBO остатки | 1 | 60 | | | | |
| Яндекс FBO продажи | 1 | 60 | 14 | | | |
| Яндекс FBO остатки | 1 | 120 | | | | |

Строки задач ищутся в диапазоне 21–80 и отбираются по имени, поэтому между ними
могут лежать посторонние таблицы — они будут пропущены. Имя должно совпадать
с колонкой «Задача» посимвольно, иначе строка молча не запустится.

Колонка **G** блока задач — «С даты». Заголовок в книге нужно завести вручную:
без него сервис поле просто не увидит и будет работать от глубины.

**Вкл** — `1` включает, пусто или `0` выключает.
**Каждые** — минимальный интервал между запусками.
**Глубина** — на сколько дней назад смотреть. Для продаж это ещё и окно, в котором
освежаются статусы уже загруженных заказов.
**С даты** — явное начало периода, `01.08.2026`. Пока поле заполнено, оно перебивает
глубину: каждый прогон тянет весь период заново. Нужно для разовой перезаливки —
**после первой успешной заливки колонку надо очистить**, иначе месяц истории будет
загружаться каждый час и упрётся в лимиты. Пока поле стоит, сервис пишет об этом в лог.

Колонки «Последний запуск» и «Результат» сервис пишет сам — туда же попадает текст
ошибки, если что-то пошло не так.

Время в книге — московское, независимо от того, в каком поясе запущен сервис.

### Разовая пересборка листа

Листы продаж пишутся upsert-ом: строка, однажды попавшая на лист, остаётся там
навсегда. Если формат данных изменился, старые строки сами не обновятся.

Чтобы задача собрала свой лист заново, напишите в её строке в колонке
«Последний запуск» слово `сброс` вместо отметки времени. На ближайшей минутной
проверке задача очистит свой лист (шапку не трогает), расширит окно до 60 дней
и загрузит данные заново. Прогон затирает ячейку своим результатом, поэтому
сброс срабатывает ровно один раз — возвращать значение вручную не нужно.

Глубже 60 дней собрать нельзя: столько отдаёт API Ozon по дате создания
отправления. Листам остатков сброс не нужен, они и так перезаписываются целиком.
Если у задачи заполнена «С даты», период берётся из неё, а не из окна сброса.

## FBO

Кроме FBS сервис тянет FBO — товар, лежащий на складе площадки: `OZON FBO`,
`WB FBO` (склады WB) и `ЯМ FBO` (FBY у Яндекса). Лист Яндекса называется
**«ЯМ FBO продажи»**, а задача — **«Яндекс FBO продажи»**: это разные строки.

FBY у Яндекса — отдельный магазин со своим `campaignId`, поэтому в доступах есть
отдельная строка «Яндекс campaignId FBY». Если подставить туда FBS-кампанию,
метод вернёт пустой список без ошибки — задача остатков это заметит и упадёт
с внятным текстом, а не сотрёт лист.

Wildberries раскидан по трём хостам со своими лимитами:

| Что | Хост | Лимит |
|---|---|---|
| заказы FBO | `statistics-api` | 1 запрос в минуту |
| остатки FBO | `seller-analytics-api` | 3 запроса в минуту |
| карточки товаров | `content-api` | 100 запросов в минуту |

Не запускайте «WB FBO продажи» одновременно с «WB остатки» — они делят лимит
`statistics-api`.

Прежний метод остатков `/api/v1/supplier/stocks` отключён 23.06.2026 и отвечает 404.
Пришедший на замену `stocks-report/wb-warehouses` не отдаёт ни штрихкод, ни артикул
продавца — только `nmId` и `chrtId`, поэтому задача остатков сперва выгружает карточки
товаров и добирает их оттуда. Разбивки по складам в новом методе пока нет: WB отдаёт
одно значение «Склад WB» на все позиции.

## Запуск локально

```bash
npm install
cp .env.example .env      # заполнить
node --env-file=.env src/index.js --once                  # один проход
node --env-file=.env src/index.js --task "OZON остатки"   # одна задача принудительно
```

## Устройство

```
src/schemas.js   структура листов и ключи upsert — единственный источник правды
src/sheets.js    авторизация, чтение, запись, upsert
src/config.js    чтение листа «Настройки»
src/http.js      запросы с повторами на 429 и 5xx
src/ozon.js      продажи и остатки Ozon
src/wb.js        продажи и остатки Wildberries
src/yandex.js    продажи и остатки Яндекс Маркета
src/index.js     планировщик: раз в минуту смотрит, что пора запускать
```

Листы продаж пишутся через **upsert** по ключу: существующие строки обновляются,
новые дописываются. Листы остатков **перезаписываются целиком** — остаток это снимок
на момент запроса, а не история.

Сервис пишет только в колонки своей схемы. Всё, что правее, не трогается никогда —
там можно держать свои формулы.

## Что важно помнить

**WB отдаёт задания без актуального статуса.** Статусы добираются вторым запросом
и только по незакрытым заданиям. Поэтому строки со статусом «Получено покупателем»,
«Отменено» и «Брак» больше не перезапрашиваются.

**Яндекс отдаёт даты как ДД-ММ-ГГГГ.** Разбираются вручную: `new Date()` понял бы
`10-12-2019` как 12 октября.

**У Ozon разбивка остатков по складам разная для разных продавцов.** Сначала
пробуется `/v2/product/info/stocks-by-warehouse/fbs`, при ошибке — `/v1/`.

**WB спрашивает остатки только по переданному списку баркодов.** Список берётся
из колонки A листа «Общая инфо», поэтому товар, которого нет в справочнике,
в остатках не появится.
